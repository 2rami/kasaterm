# Claude 계정 갱신을 관문 하나가 맡기

카사 계정이 같은 기기는 그 계정에 딸린 Claude 로그인을 다시 로그인하지 않고 바로 쓴다.
갱신 토큰(refresh token)은 관문만 쥐고, 기기는 짧은 접근 토큰(access token)만 받는다.

배경: 2026-09-28 에는 「목록만 나누고 로그인은 기기마다」로 갔다(`agent_accounts.rs` 머리말).
갱신 토큰은 한 번 쓰면 바뀌어서 기기끼리 나누면 먼저 갱신한 쪽이 나머지를 로그아웃시키고,
`claude setup-token` 은 `user:inference` 권한뿐이라 커넥터·Chrome·사용량이 꺼지기 때문이다.
이번 길은 둘 다 피한다 — 사슬은 하나(관문)만 돌리고, 기기에는 정식 로그인과 같은 권한의 접근 토큰을 준다.

## 실측 (claude 2.1.292, 2026-10-07)

실험 슬롯 `~/.config/kasaterm/claude-lab/relay-probe` 를 만들고, 실제 슬롯의 **접근 토큰만** 복사해
(갱신 토큰 없이) `CLAUDE_SECURESTORAGE_CONFIG_DIR`·빈 `CLAUDE_CONFIG_DIR` 로 띄웠다. 사용자 슬롯과
기본 자리는 읽기만 했다. 실험 뒤 그 키체인 항목은 지웠다.

| 경우 | 결과 |
|---|---|
| 접근 토큰만, 만료 7.8시간 남음 | `-p` 응답 정상, `auth status` 로그인(max) |
| 만료 2분 남음(claude 의 5분 갱신 기준 안) | 갱신 시도 없이(`no_refresh_token`) 그대로 응답, 항목 안 바뀜 |
| 저장된 만료 시각이 10분 지남(서버에선 유효) | 그대로 응답, 로그아웃 안 함 |
| 무효 접근 토큰, 갱신 토큰 없음 | `401 OAuth access token is invalid` 로 그 요청만 실패, **항목은 그대로** |
| 무효 접근 토큰 + 죽은 갱신 토큰 | 갱신 거부(invalid_grant) 뒤 claude 가 항목을 **빈 토큰 껍데기로 지움** — 로그아웃 |
| 도는 claude 아래에서 항목을 바꿔 끼움 | 재시작 없이 다음 요청부터 새 토큰을 씀(키체인 읽기 캐시 30초) |
| 신원 `/api/oauth/profile`·사용량 `/api/oauth/usage` | 둘 다 200 |
| claude.ai 커넥터(`claude mcp list`) | 9개 모두 Connected |

바이너리에서 확인한 근거:
- 갱신은 저장소에 갱신 토큰이 있을 때만 한다. 없으면 만료 직전에도 `no_refresh_token` 으로 끝나고
  아무것도 지우지 않는다. 지우기(`bmr`)는 「서버가 거부한 그 갱신 토큰이 저장소에 그대로 있을 때」만 한다.
- 요청 전 점검이 매번 저장소를 다시 읽는다(키체인 읽기는 30초 캐시). 401 때도 캐시를 버린다.
- 권한·구독 표시는 저장소의 `scopes`·`subscriptionType` 을 그대로 믿는다. 정식 로그인 토큰의 권한
  (`user:profile`·`user:mcp_servers`·`user:plugins`…)이 그대로라 기능이 안 꺼진다.
- 키체인은 claude 도 `security` 명령으로 읽고 쓴다(값은 `security -i` 표준입력). 우리가 같은 명령으로
  써도 암호 창이 안 뜬다.
- 같은 키체인 항목에 MCP 서버 OAuth(`mcpOAuth`)도 산다 — 덮을 때 `claudeAiOauth` 만 바꾼다.
- 갱신 토큰 유무로 갈리는 것: 원격 조종 자격 판정의 텔레메트리 끈 경우 폴백(평소엔 GrowthBook 이 정함),
  권한 확장 재로그인(`no_refresh`). 일상 기능에는 영향이 없다.
- 접근 토큰 수명은 8시간, 갱신 토큰의 `refreshTokenExpiresAt` 은 로그인 +30일이다(서버가 그날 끊는지는 미확인).

## 흐름

```
기기 A (로그인한 슬롯, 갱신 토큰 있음)
  └─ POST /relay/agent-chains/seal ── 관문이 그 접근 토큰으로 /api/oauth/profile 을 물어 신원 확인
       └─ 사슬 봉인(AES-256-GCM, 관문 계정별 파일 agent-chains/<계정>.sealed)
       └─ 답을 받으면 A 의 슬롯에서 갱신 토큰 칸을 지운다
관문 (유일한 갱신자)
  └─ 1분마다: 남은 시간이 3시간 아래인 사슬을 갱신(사슬 전체를 한 줄로)
기기 A·B·C (같은 카사 계정)
  └─ 5분마다 GET /relay/agent-chains → 접근 토큰만 받아 자기 슬롯에 쓴다
       └─ 도는 claude 는 30초 안에 새 토큰을 집는다
```

- 기기 토큰이 있어야 한다. 폐기된 기기·막힌 계정은 401. 다른 관문 계정의 사슬은 안 보인다.
- 응답에 갱신 토큰은 없다. 로그·감사 기록(`agent-chains/audit.jsonl`)·argv 에도 토큰은 안 남는다
  (감사에는 계정·기기·사슬 열쇠·결과만).
- 사슬 열쇠는 `agent_accounts::account_key` 와 같다(팀 조직은 조직명, 개인은 이메일). 기기가 적어 보낸
  신원은 믿지 않고 관문이 프로필에서 만든다.
- 맡긴 토큰으로 신원을 못 읽으면 422(`token_rejected`)다. 401 이 아닌 까닭: 기기는 401 을 「관문 로그인이
  풀렸다」로 읽고 관문 로그인을 버린다.
- 같은 계정의 멀쩡한 사슬이 이미 있으면 새 사슬로 갈지 않고 그 접근 토큰을 돌려준다(`held: true`).
  끊긴 사슬(`reconnect_required`)만 새로 맡긴 것으로 바뀐다.

### 기기 쪽 규칙 (`agent_chains.rs` 기기 절)

앱이 도는 동안 5분마다(로그인 직후·「다른 기기 계정」 단추 뒤에는 곧바로) 한 번 돈다. 슬롯마다 실제
저장소를 본다 — 작업대에 실린 활성 계정은 기본 자리, 나머지는 슬롯 자리(`agent_accounts::claude_store`).

1. **맡기기**: 갱신 토큰이 있고 접근 토큰이 30분 넘게 남은 슬롯은 관문에 내민다. 관문이 맡았으면
   (`held: false`) 그 슬롯에서 갱신 토큰 칸만 지우고, 이미 같은 계정 사슬이 있으면(`held: true`) 관문
   접근 토큰으로 바꾸고 자기 사슬은 버린다. 쓰기 직전에 다시 읽어 갱신 토큰이 그대로일 때만 쓴다 —
   그 사이 claude 가 회전시켰으면 이번 것은 낡았으니 다음 주기에 새것을 내민다.
2. **받기**: 갱신 토큰이 없는 슬롯(접근 토큰만 있거나, claude 가 죽은 사슬에 남기는 빈 토큰 껍데기)은
   그 계정 사슬이 관문에 멀쩡히 있고 더 새 토큰이면 덮는다. 계정은 맡기기·받기로 적어 둔 표
   (`agent-chains.json`, 슬롯 → 열쇠, 토큰 없음) → 없으면 앱이 확인해 둔 슬롯 신원
   (`claude_account_emails`·`_orgs`) 순으로 찾는다. 키체인 항목조차 없는 슬롯은 사람이 고른 것만 채운다.
3. 이 기기에 없는 계정은 설정 「다른 기기에 있는 계정」 줄의 「로그인」 한 번으로 새 슬롯에 받는다
   (관문이 그 사슬을 쥐고 있으면 브라우저 없이). 사슬이 없으면 예전처럼 브라우저 로그인.

- 갱신 토큰 칸은 **지운다**. 빈 문자열("")로 두면 claude 가 죽은 사슬 표시로 읽는다.
- 같은 항목의 다른 칸(`mcpOAuth` 등)은 그대로 둔다.
- 키체인을 못 읽었으면(잠김 등) 안 덮는다. 쓰기 직전에 그 슬롯이 아직 같은 자리를 가리키는지(그 사이
  계정을 바꿨는지) 다시 본다.
- 키체인 쓰기는 claude 와 같은 `security -i` 표준입력(값은 hex)이다. 한 줄 상한 4032자를 넘는 항목은
  argv 로 넘기지 않고 건너뛴다(실측 항목은 1.2~1.4KB).
- 관문이 이 창구를 모르는 옛 판이면(404) 아무것도 바꾸지 않는다 — 앱을 먼저 깔아도 안전하다.
- 검증 리그(격리 env)에서는 돌지 않는다.

### 왜 이 순서인가

- 봉인 직후 관문이 바로 갱신하지 않는다. 그 사이 기기의 도는 claude 가 메모리 캐시의 옛 갱신 토큰을
  쓸 수 있는데(최대 30초), 같은 토큰이 두 번 쓰이면 서버가 사슬 전체를 끊을 수 있다. 관문은 남은 시간이
  3시간 아래로 내려올 때 처음 갱신한다. 봉인을 30분 넘게 남았을 때만 하는 것도 같은 이유다
  (claude 는 5분 안쪽에서만 스스로 갱신한다).
- 기기는 늘 관문에서 받아 오고(pull) 관문이 밀지 않는다. 관문이 3시간 앞서 갱신하므로 5분 간격이면
  기기 토큰은 늘 2시간 55분 이상 남는다. 관문이 3시간 가까이 꺼져도 기기는 안 끊긴다.
- 관문이 오래 꺼져 토큰이 끝나도 로그아웃(키체인 지우기)은 안 일어난다 — 기기에 갱신 토큰이 없어서다.
  관문이 돌아오면 다음 받기에 이어진다.

## 실패와 복구

| 상황 | 동작 |
|---|---|
| 관문 갱신이 거부됨(invalid_grant) | 그 사슬을 「다시 로그인」으로 표시. 기기 토큰이 끝나면 슬롯이 「로그인 필요」. 아무 기기에서 다시 로그인하면 규칙 3 으로 새 사슬을 맡긴다 |
| 관문 갱신이 일시 실패(429·5xx·네트워크) | 다음 주기에 다시. 남은 시간이 3시간이라 여러 번 기회가 있다 |
| 봉인은 됐는데 기기에서 갱신 토큰 빼기 실패 | 다음 주기에 다시 내밀면 `held: true` 로 관문 토큰을 받고 뺀다(관문 첫 갱신은 몇 시간 뒤) |
| 관문 갱신이 일시 실패 | 그 사슬만 5분 쉬고 다시 |
| 관문 프로세스 둘 | 봉인 저장소가 단일 쓰기 잠금(flock)이라 둘째는 이 기능이 꺼진 채 뜬다 |
| 30일 절대 만료(미확인) | 끝나기 전 표시 → 한 기기에서 다시 로그인 → 규칙 3 |

## 알림 — 사슬 하나가 막히면 그 계정을 쓰는 모든 기기가 함께 끊긴다

- **관문 → 폰**: 갱신이 거부돼 사슬이 끊기면, 또는 일시 실패가 이어져 접근 토큰이 1시간 안 남았는데 아직
  갱신을 못 했으면 그 관문 계정의 폰으로 푸시를 보낸다(원격 승인과 같은 APNs 길, `thread-id`
  `agent-chains`, 사슬마다 한 자리). 「막혔어요」는 사슬마다 한 번, 갱신에 성공하면 다시 울릴 수 있다.
- **기기 → 데스크톱 알림·토스트**: 관문이 멈추면 관문은 알리지 못한다. 그래서 각 기기도 관문에서 받아 쓰는
  슬롯의 토큰이 1시간 안 남았거나 끝났으면(「관문에 닿지 않아」/「관문이 갱신하지 못해」), 또는 관문이 그
  사슬을 「다시 로그인」으로 보이면 알린다. 계정마다 한 번, 풀리면 잊는다. 관문 로그인이 없을 때도 본다.
- 관문은 3시간 앞서 갱신하므로 1시간 알림까지 2시간의 여유가 있다. 알림을 받으면: 관문이면
  `tools/kasa-gateway-seoul/gateway.sh status`, 사슬이 끊겼으면 아무 기기에서 그 계정 한 번 다시 로그인.

## 첫 실제 갱신 확인

관문은 접근 토큰이 3시간 안 남은 사슬부터 갱신한다(맡긴 직후 2분은 쉰다). 맡긴 토큰이 몇 시간 남았느냐에
따라 첫 갱신은 교체 뒤 0~5시간 사이에 일어난다.

```sh
ssh kasanet-relay 'sudo tail -n 20 /var/lib/kasa-relay/agent-chains/audit.jsonl'   # action=refresh result=ok
ssh kasanet-relay 'sudo journalctl -u kasa-relay --since -6h -o cat | grep agent-chains'  # 실패만 찍힌다
```

`result` 가 `ok` 면 실제 토큰 창구가 관문 IP 에서 받았다는 뜻이다. `reconnect_required` 면 그 사슬이 거부됐고,
`stalled` 면 일시 실패가 이어지는 중이다. 기기 쪽에서는 `GET /relay/agent-chains` 의 `updated` 가 맡긴 시각에서
바뀐다. 감사 줄에는 토큰이 없다.

## 검증 (2026-10-07)

- 관문·기기 시험 12개(`agent_chains/tests.rs`·`gateway_agent_chains/tests.rs`): 가짜 Anthropic 창구로
  봉인·신원 열쇠·`held`·앞당겨 갱신·거부 표시·429 쉬기, 기기 셋(메모리 저장소)이 실제 관문 라우터와 맞붙어
  맡기기→받기→한 번 회전→모두 새 토큰, 맡긴 뒤 claude 가 회전한 슬롯은 안 덮음, 옛 관문(404)이면 그대로.
  응답·봉인 파일·감사 기록에 토큰이 없는지도 본다.
- 실제 키체인 쓰기: 실험 슬롯에 `security -i` 로 쓴 항목(갱신 토큰 칸 없음)을 claude 2.1.292 가 읽어
  `auth status` 로그인·`-p` 응답·커넥터 9개 정상. 실험 항목은 지웠다.
- 서울 관문 IP 에서 토큰 창구: 가짜 갱신 토큰에 400 `invalid_grant`(정상 처리, 막힘 없음). curl 기본 UA 는 429
  라 관문은 자기 UA(`KASA-AgentChains/1`)로 부른다. 운영 관문 교체 2026-10-07 15:05([seoul-gateway.md](seoul-gateway.md)).
- 미확인: 관문의 실제 갱신 POST(새 앱 판을 받은 기기가 사슬을 맡긴 뒤 0~5시간 안), 30일 절대 만료.

## 범위 밖

- Codex: 접근 토큰 240시간·`last_refresh` 8일 기준으로 스스로 갱신한다. 접근 토큰만 둔 `auth.json` 에서
  codex 가 어떻게 도는지는 이번에 재지 않았다. 다음 단계.
- 관문이 기기로 미는 길(업링크 채널)은 안 만들었다 — 5분 받기로 여유가 충분하다.
