# 화면 스트리밍 — Parsec 급 기기 화면 보기

기기 화면 거울(`docs/screen-mirror.md`)은 CPU JPEG 를 웹소켓으로 8fps 에 보낸다. 이 문서는 그것을 하드웨어 영상 압축과
카사넷 QUIC 으로 바꿔 「선명하고 빠른」 화면 보기로 가는 길이다. 단계마다 잰 숫자를 남긴다.

## 단계

| 단계 | 내용 | 끝 조건 |
|---|---|---|
| S0 | 측정기 `spikes/screen-stream` — ScreenCaptureKit + VideoToolbox + iroh QUIC. 지연·선명도·대역폭 | 맥북↔미니 수치를 이 문서에 기록 |
| S1 | 맥 → 맥: 카사텀 칸 안에서 네이티브로 보기(웹 칸이 아니다). 직통이 아니면 지금 JPEG 거울로 | 격리 앱 둘에서 60fps·지연 측정 — 됐다(아래 「S1」) |
| S1b | 화면 칸에서 조작(마우스·키·글자) — 기존 거울의 조작 메시지·`screen_input` 을 그대로 싣는다. GPU 복사 없애기(IOSurface → Metal) | |
| S2 | 폰에서 보기 — `kasa-net-ffi` 에 풀기를 더한다 | 실기에서 60fps |
| S3 | Windows 뜨기·압축(DXGI·Media Foundation)과 보기 | |
| S4 | 소리·클립보드·상대 마우스·패드 | |

## S0 측정기

```
screen-stream id --key PATH                                   # 보는 쪽 id
screen-stream serve --allow ID[,ID…] [--relay URL]            # 보내는 쪽 — 화면 기록 권한이 있는 앱(카사텀 칸) 안에서
screen-stream view <ADDR> --key PATH [--secs N] [--codec hevc|h264] [--mbps N] [--fps N] [--pix bgra|420v]
                  [--scale 0.1-1] [--no-lowlat] [--no-realtime] [--flush] [--refine N] [--scroll PX] [--dump DIR]
```

- 설정은 보는 쪽이 붙을 때 보낸다. serve 는 한 번 띄워 두고 view 만 바꿔 가며 잰다. serve 는 `--allow` 의 id 만 받는다
  (`kasa_net::builder` 허용 목록 훅) — 화면에는 메일·비밀번호 창까지 보인다.
- 장마다 단방향 QUIC 스트림 하나. 옛 장일수록 우선순위를 높여 순서대로 간다. 압축은 키프레임을 보는 쪽이 청할 때만 낸다.
- 시계: 보는 쪽이 설정을 보내기 **전에** 핑 30번으로 두 기기 호스트 시계 차이를 잡는다(왕복이 가장 짧은 핑). 장이 흐르는
  중에 맞추면 그동안 쌓인 첫 장들의 전송 시간이 부풀려진다.
- 구간: 화면→SCK(SCK 프레임 PTS 부터 콜백까지) · SCK→압축 끝 · 압축 끝→받음(시계 차이 보정) · 받음→풀림(VT 동기 풀기,
  BGRA IOSurface 까지). **화면에 그리기(보는 쪽 디스플레이)는 빠져 있다** — S1 에서 잰다. 요약은 첫 1초와 키프레임을 뺀다.
- `--scroll PX`: 보내는 쪽이 마지막 화면을 장마다 PX 줄씩 밀어 60fps 로 만든다. 사람 화면을 건드리지 않고 화면 가득
  글자가 움직이는 경우를 잰다. 300 은 장마다 내용이 크게 바뀌는 험한 경우다.
- `--refine N`: 화면이 멈추면 같은 장을 N 번 더 압축해 보낸다(아래 「정지 화면 다듬기」).
- `--dump DIR`: 끝에 원본 마지막 장(PNG)을 받아 풀린 같은 장과 밝기(Y) PSNR 을 낸다. 스크롤 시험이면 그 순간 스크롤을 멈춘다.

## S0 실측 (2026-11-16)

보내는 쪽 맥북 Pro M3 Max(내장 화면 3024×1964, Wi-Fi), 받는 쪽 같은 맥북(루프백)과 맥 미니 M4(같은 망 직통, 맥북
`192.168.1.28` 로 직통이 섰다). 기본 HEVC · VT 저지연 모드 · 30Mbps · 60fps · 원래 해상도. 화면은 실제 작업 화면
(학생 칸들 출력)이라 거의 멈춰 있어 움직임은 `--scroll` 로 만들었다.

### 지연 — 미니가 받기(같은 망 직통)

| 경우 | 실제 Mbps | 화면→풀림 p50 / p90 / p99 | 압축 p50 | 전송 p50 | 풀기 p50 | 새 장 크기 p50 |
|---|---|---|---|---|---|---|
| 실제 화면(거의 멈춤) | 0.7 | 26.6 / 35.4 / 35.5ms | 17.2 | 2.9 | 4.2 | 2KB |
| 스크롤 8줄/장 | 1.6 | 24.6 / 27.3 / 35.3ms | 16.8 | 3.1 | 3.6 | 2KB |
| 스크롤 300줄/장 · 30Mbps | 29.6 | 26.5 / 29.0 / 36.4ms | 16.8 | 5.3 | 3.6 | 60KB |
| 스크롤 300줄/장 · 60Mbps | 59.1 | 30.9 / 34.8 / 50.7ms | 16.8 | 9.0 | 4.1 | 123KB |

- 60fps 그대로(59fps) 나왔고 비트레이트는 목표를 정확히 따른다(저지연 모드의 율 제어).
- 큰 장은 실어 나르는 시간이 붙는다 — 123KB 장은 Wi-Fi 에서 전송 p50 이 9ms 다. 대역폭은 지연이기도 하다.
- 첫 키프레임은 150~330ms(풀기 세션 만들기 약 100ms + 키프레임 압축 40~120ms). 붙을 때 한 번이다.

### 압축 시간이 바닥이다

루프백(같은 맥, 전송 0.2ms)에서 압축 설정을 바꿔 봤다. **합계의 대부분은 압축 17ms 다.**

| 바꾼 것 | 압축(SCK→압축 끝) p50 | 합계 p50 |
|---|---|---|
| 기본(3024×1964, 590만 화소) | 17.5ms | 21.9ms |
| `--scale 0.833`(2518×1636) | 13.2ms | 23.9ms |
| `--scale 0.667`(2018×1310) | 9.7ms | 14.2ms |
| `--scale 0.5`(1512×982) | 9.8ms | 13.2ms |
| H.264 | 16.4ms | 20.1ms |
| 저지연 모드 끔 | 15.8ms(p90 28.8) | 28.0ms |
| `--pix 420v`(BGRA→YUV 변환 없음) | 17.4ms | 21.4ms |
| `--fps 120` | 17.9ms | 23.6ms |
| RealTime 끔 · 장마다 `complete_frames` | 17.7~18.5ms | 25~32ms |
| 멈춘 동안에도 60fps 로 계속 압축 | 21.8ms | 26.2ms |

- 압축은 약 10ms 고정에 화소에 비례하는 몫이 붙는다. 0.667 배 아래로는 줄지 않는다. fps·RealTime·장마다 비우기·420v
  어느 것도 바닥을 못 내린다 — 하드웨어 인코더의 한 장 처리 시간으로 본다.
- 인코더는 한 장씩 처리한다. 멈춘 화면을 계속 압축하면 새 장이 앞 장을 기다려 오히려 느려진다(17.5 → 21.8ms).
- 저지연 모드를 끄면 p50 은 비슷해도 p90 이 튀고 장이 6~40배 커진다(작은 갱신에도 큰 장). 저지연 모드를 쓴다.
- 저지연 모드에서는 `MaxFrameDelayCount`·`PrioritizeEncodingSpeedOverQuality` 가 `-12900`(지원 안 함)이고
  `UsingHardwareAcceleratedVideoEncoder` 를 읽을 수 없다. 끄면 하드웨어로 읽힌다.

### 선명도 — 밝기(Y) PSNR

| 경우 | 전체 | 글자 많은 곳 |
|---|---|---|
| 실제 화면, 멈춤, 30Mbps | 52.0dB | 45.9dB(400×200, 2 배로 눈으로 봐도 빨간 코드 글씨까지 같다) |
| 스크롤 300 뒤 멈춤, 30Mbps, 다듬기 없음 | 32.9dB | 35.4dB(글자 상자 테두리·아이콘이 뭉갠다) |
| 같은 경우, 다듬기 10장(0.17초) | 48.1dB | 51.4dB |
| 같은 경우, 다듬기 30장(0.5초) | 51.9dB | 55.7dB |
| 같은 경우, 다듬기 60장 | 51.8dB | 55.5dB |
| 스크롤 300 뒤 멈춤, 60Mbps, 다듬기 없음 | 40.0dB | 44.6dB |
| 미니가 받기, 스크롤 300 뒤 멈춤, 30·60Mbps, 다듬기 30장 | 51.7·51.8dB | 55.1·56.0dB |

- 4:2:0 HEVC 로도 레티나 원래 해상도면 멈춘 화면은 원본과 구분이 안 된다. Parsec 도 mac 호스트는 4:2:0 이다(4:4:4 는
  Windows + NVIDIA/Intel 호스트에서만, Teams·Warp 요금제).
- **정지 화면 다듬기**: 움직이던 화면이 멈추면 SCK 는 새 장을 안 준다. 마지막 장은 움직일 때의 낮은 품질로 남는다.
  같은 장을 30장(60fps 로 0.5초) 더 압축하면 율 제어가 남는 비트로 품질을 올려 멈춘 화면 기준선까지 돌아온다.
  다듬기 장은 장마다 1~2KB 라 대역폭 부담이 없다. 계속 보내면(Parsec 의 Constant FPS) 위의 「멈춘 동안에도 계속 압축」처럼
  새 장의 지연이 늘어 30장에서 멈춘다.

### 재지 못한 것

- **눈에 닿기까지(유리→유리)**: 보는 쪽 화면 그리기·주사 시간. S1 의 네이티브 칸에서 잰다.
- **국내 중계 길**: 중계 서버에 EndpointId 허용 목록이 있어(`docs/kasanet.md` 「허용 목록」) 측정기의 임시 키로는 못 붙는다.
  재려면 측정기 id 를 중계 허용 목록에 잠깐 넣어야 한다. n0 공용 중계는 데이터 길이 아니라 재지 않았다.
- **다른 망 너머 직통**(인터넷 구멍 뚫기): 이번 직통은 같은 망이었다. 카사넷 P0 에서 다른 망 직통 왕복 6~8ms 를 쟀다.
- 영상·게임처럼 화면 전체가 새로 그려지는 실제 내용, 여러 화면, 폰 풀기, Windows.

## S1 로 가져갈 결정

- **HEVC · 저지연 모드 · 원래 해상도 · 30Mbps 기본**에 정지 화면 다듬기 30장. 빠른 망이면 60Mbps 로 올려 움직이는 동안의
  선명도(33 → 40dB)를 산다. 지연이 더 중요하면 0.667 배로 압축 8ms 를 아낀다(보는 쪽이 키워 그린다).
- 키프레임은 붙을 때와 풀기 실패 때만. 풀기 세션은 첫 키프레임에 만든다(약 100ms, 한 번).
- 직통에서는 장마다 신뢰 스트림으로 충분했다(손실 없음, p99 36ms). 손실 많은 길에서는 늦은 장을 버리고 키프레임을 청하는
  쪽으로 바꾼다 — 지금 압축은 매 장이 앞 장을 참조해 장을 버리면 다음 키프레임까지 화면이 깨진다.
- 보는 쪽은 웹 칸이 아니라 카사텀 칸 안에 네이티브로 그린다 — VT 가 내는 IOSurface 를 Metal 텍스처로 바로 쓴다(복사 없음).

## S1 — 카사텀 칸 안에서 보기 (2026-11-16)

### 흐름

```
보는 앱  Info 「화면 거울」 ─ machinescol.rs open_screen_mirror
  └ screen_stream::can_view(base)?  (이 판 macOS · 그 기기 /version kasanet.screen · 카사넷 직통·믿는 중계)
       ├ 아니면 → 지금 JPEG 웹 칸
       └ 맞으면 → open_screen_pane → ScreenView::open → kasa_remote::screen_stream::watch
                    kasanet::connect(base, "kasa/screen/1")  ── QUIC ──▶  그 기기 ScreenAccept → screen_stream::serve
                    풀기 일꾼(view.rs, VT) ◀── 장마다 단방향 스트림 ──  Host(host.rs): SCK 420v → VT HEVC
                    GUI(pane.rs paint): 새 장만 BGRA 로 GPU 에 올려 칸 본문에 비율 맞춰 그림
```

### 계약 (`kasa_remote::screen_stream`)

- 제어 스트림 `[u8 종류][u32 길이][내용]` — `P` 핑(보는 쪽 시계)·`p` 퐁(+보내는 쪽 시계)·`C` 설정 JSON·`I` 압축 정보 JSON·
  `K` 키프레임 청·`X` 거절 `{reason: permission|unavailable}`·`Q` 끝. 보는 쪽은 **핑 20번으로 시계를 맞춘 뒤** 설정을 보낸다.
- 장 `'F'` + seq·cap_id·key·t_cap·t_enc·가로·세로·파라미터 셋 + AVCC/HVCC NAL. 옛 장일수록 우선순위가 높다.
- 설정 `{codec, bitrate, fps, scale, refine}` — 보내는 쪽이 범위로 깎는다(1–200Mbps·1–120fps·0.25–1·다듬기 ≤240). 기본은
  S0 결정 그대로(HEVC 30Mbps 60fps 원래 해상도, 다듬기 30장).
- 못 보낸 장이 8장 쌓이면 다 버리고 키프레임부터 — 장마다 앞 장을 참조해 골라 버릴 수 없다. 보는 쪽은 풀기에 실패하면 키프레임을
  청하고 그 전 장은 버린다.
- 보내는 쪽은 거절 까닭을 쓰고 연결이 닫힐 때까지(최대 3초) 기다린다 — 바로 돌아가면 연결이 먼저 닫혀 보는 쪽은 「끊김」만 봤다
  (시험이 잡았다).
- 화면 기록 권한이 없으면 `permission` 을 알리고 연결마다 한 번 그 기기 앞에 권한 창을 띄운다. 칸에는 「그 기기 카사텀에 화면 기록
  권한이 없어요」.

### 칸

- `PaneContent::Screen { label, view_id }` 는 연 칸의 앞 탭이다. 연결·풀린 장은 `App.screen_views`(Workspace 는 PTY 스레드와
  공유라 실물을 못 둔다 — 웹 칸과 같은 까닭). `sync_screen_views` 가 루프마다 **창 트리에 실재하는 탭만** 연결을 쥐게 한다 —
  닫혀 되살리기 목록으로 물러난 탭은 연결을 버리고, 되살아나면 다시 붙는다.
- 재시작하면 화면 탭은 복원되지 않는다(세션 기록은 PTY 칸 기준이라 그 칸의 터미널만 남는다). 다시 연다.
- 아직 보기만 한다. 화면 탭이 앞이면 키를 어디에도 보내지 않는다.
- 새 장은 풀기 일꾼이 `UserEvent::Redraw` 로 GUI 를 깨운다. GUI 는 그 장을 줄 간격 그대로 `Bgra8Unorm` 텍스처에 올린다
  (`GridRenderer::update_image_bgra`, RGBA 로 바꿔 담지 않는다).

### 실측 — 격리 앱 둘, 같은 맥(M3 Max), release

원본 리그 B 가 실제 화면(3024×1964)을 보내고 보는 리그 A 가 칸으로 본다. 카사넷은 루프백 직통(왕복 1ms).

| 경우 | 새 장 fps | 화면→풀림 p50 | GPU 올리기 | GUI 가 올린 장 |
|---|---|---|---|---|
| 실제 화면(거의 멈춤) | 1–3 | 21ms | 2.4ms | 새 장마다 |
| 검증 스크롤 8줄/장 | 60–61 | 21–22ms | 2.8–3.4ms | 초당 약 60 |
| 검증 스크롤 300줄/장 · 30Mbps | 60–61 | 21ms | 2.1–2.7ms | 초당 56–60 |

- 칸을 닫으면 보는 쪽 연결이 닫히고 보내는 쪽 뜨기·압축이 멈춘다(B CPU 6.6% → 2.3%, 스레드 52 → 48).
- 화면→풀림에는 GPU 올리기(약 3ms)와 화면에 내보내기가 빠져 있다. 600만 화소 장을 장마다 CPU 로 한 번 복사하는 값이라 S1b 에서
  IOSurface 를 Metal 텍스처로 바로 쓰면 없어진다.

### 리그

- 리그 포트는 실행마다 바뀌어 서로의 명부에 미리 못 적는다. 고정 포트 TCP 중계 둘(47821→A, 47822→B)을 먼저 띄우고 명부에는 그
  주소를 적는다 — 카사넷은 루프백 base 로 물은 `/version` 의 id 만 배우므로 중계를 거쳐도 그대로 배운다.
- 둘 다 `docs/verify-app.md` 격리 env + `KASATERM_KASANET_BIND=127.0.0.1:0`. B 는 화면 기록 권한이 있는 앱(카사텀 칸) 안에서 띄운다.
- A 에 `KASATERM_TEST_SCREEN_LABEL=<B 라벨>` 이면 직통이 선 뒤 화면 칸을 열고 2초마다 `[screen-view-test] … hud=60fps · 21ms · 직통
  upload=2.6ms uploads=N` 을 로그에 적는다(`testkit.rs run_pending_screen_view_test`).
- B 에 `KASATERM_TEST_SCREEN_SCROLL=<줄>` 이면 사람 화면을 건드리지 않고 마지막 화면을 장마다 밀어 60fps 로 움직이는 화면을 만든다
