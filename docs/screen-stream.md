# 화면 스트리밍 — Parsec 급 기기 화면 보기

기기 화면 거울(`docs/screen-mirror.md`)은 CPU JPEG 를 웹소켓으로 8fps 에 보낸다. 이 문서는 그것을 하드웨어 영상 압축과
카사넷 QUIC 으로 바꿔 「선명하고 빠른」 화면 보기로 가는 길이다. 단계마다 잰 숫자를 남긴다.

## 단계

| 단계 | 내용 | 끝 조건 |
|---|---|---|
| S0 | 측정기 `spikes/screen-stream` — ScreenCaptureKit + VideoToolbox + iroh QUIC. 지연·선명도·대역폭 | 맥북↔미니 수치를 이 문서에 기록 |
| S1 | 맥 → 맥: 카사텀 칸 안에서 네이티브로 보기(웹 칸이 아니다). 직통이 아니면 지금 JPEG 거울로 | 격리 앱 둘에서 60fps·지연 측정 — 됐다(아래 「S1」) |
| S1b | 화면 칸에서 조작(마우스·휠·키·글자·붙여넣기) — 기존 거울의 조작 메시지·`screen_input` 을 그대로 싣는다 | 됐다(아래 「S1b」) |
| S1c | GPU 복사 없애기(VT 의 IOSurface → Metal 텍스처) — 됐다(아래 「S1c」). 여러 화면, 재시작 뒤 화면 탭 복원은 남았다 | |
| S2 | 폰에서 보기 — `/screen/ws` 에 영상 방식(`codec=hevc`, 직통일 때만)을 더하고 폰은 Swift 플러그인이 VT 로 풀어 Flutter `Texture` 로 그린다 | 실기에서 60fps |
| S3 | Windows 뜨기·압축(DXGI·Media Foundation)과 보기(MF 디코더·D3D11 공유 텍스처) — 됐다(아래 「S3」) | 격리 앱 둘(같은 PC)·장 덤프로 확인 |
| S3b | Windows 보안 데스크톱(UAC·잠금 화면)까지 보고 누르기 — Parsec 처럼 SYSTEM 서비스가 세션에 도우미를 띄운다(아래 「S3b」) | 시험 서비스로 UAC 창이 보이고 원격 Esc 로 닫혔다 |
| S4 | 소리·클립보드·상대 마우스·패드 | |

## S0 측정기

```
screen-stream id --key PATH                                   # 보는 쪽 id
screen-stream serve --allow ID[,ID…] [--relay URL]            # 보내는 쪽 — 화면 기록 권한이 있는 앱(카사텀 칸) 안에서
screen-stream view <ADDR> --key PATH [--secs N] [--codec hevc|h264] [--mbps N] [--fps N] [--pix bgra|420v]
                  [--scale 0.1-1] [--no-lowlat] [--no-realtime] [--flush] [--refine N] [--scroll PX] [--dump DIR]
```

- 설정은 보는 쪽이 붙을 때 보낸다. serve 는 한 번 띄워 두고 view 만 바꿔 가며 잰다. serve 는 `--allow` 의 id 만 받는다
  (`kasa_net::builder` 허용 목록 훅) — 화면에는 메일·비밀번호 창까지 보인다.
- 장마다 단방향 QUIC 스트림 하나. 옛 장일수록 우선순위를 높여 순서대로 간다. 압축은 키프레임을 보는 쪽이 청할 때만 낸다.
- 시계: 보는 쪽이 설정을 보내기 **전에** 핑 30번으로 두 기기 호스트 시계 차이를 잡는다(왕복이 가장 짧은 핑). 장이 흐르는
  중에 맞추면 그동안 쌓인 첫 장들의 전송 시간이 부풀려진다.
- 구간: 화면→SCK(SCK 프레임 PTS 부터 콜백까지) · SCK→압축 끝 · 압축 끝→받음(시계 차이 보정) · 받음→풀림(VT 동기 풀기,
  BGRA IOSurface 까지). **화면에 그리기(보는 쪽 디스플레이)는 빠져 있다** — S1 에서 잰다. 요약은 첫 1초와 키프레임을 뺀다.
- `--scroll PX`: 보내는 쪽이 마지막 화면을 장마다 PX 줄씩 밀어 60fps 로 만든다. 사람 화면을 건드리지 않고 화면 가득
  글자가 움직이는 경우를 잰다. 300 은 장마다 내용이 크게 바뀌는 험한 경우다.
- `--refine N`: 화면이 멈추면 같은 장을 N 번 더 압축해 보낸다(아래 「정지 화면 다듬기」).
- `--dump DIR`: 끝에 원본 마지막 장(PNG)을 받아 풀린 같은 장과 밝기(Y) PSNR 을 낸다. 스크롤 시험이면 그 순간 스크롤을 멈춘다.

## S0 실측 (2026-11-16)

보내는 쪽 맥북 Pro M3 Max(내장 화면 3024×1964, Wi-Fi), 받는 쪽 같은 맥북(루프백)과 맥 미니 M4(같은 망 직통, 맥북
`192.168.1.28` 로 직통이 섰다). 기본 HEVC · VT 저지연 모드 · 30Mbps · 60fps · 원래 해상도. 화면은 실제 작업 화면
(학생 칸들 출력)이라 거의 멈춰 있어 움직임은 `--scroll` 로 만들었다.

### 지연 — 미니가 받기(같은 망 직통)

| 경우 | 실제 Mbps | 화면→풀림 p50 / p90 / p99 | 압축 p50 | 전송 p50 | 풀기 p50 | 새 장 크기 p50 |
|---|---|---|---|---|---|---|
| 실제 화면(거의 멈춤) | 0.7 | 26.6 / 35.4 / 35.5ms | 17.2 | 2.9 | 4.2 | 2KB |
| 스크롤 8줄/장 | 1.6 | 24.6 / 27.3 / 35.3ms | 16.8 | 3.1 | 3.6 | 2KB |
| 스크롤 300줄/장 · 30Mbps | 29.6 | 26.5 / 29.0 / 36.4ms | 16.8 | 5.3 | 3.6 | 60KB |
| 스크롤 300줄/장 · 60Mbps | 59.1 | 30.9 / 34.8 / 50.7ms | 16.8 | 9.0 | 4.1 | 123KB |

- 60fps 그대로(59fps) 나왔고 비트레이트는 목표를 정확히 따른다(저지연 모드의 율 제어).
- 큰 장은 실어 나르는 시간이 붙는다 — 123KB 장은 Wi-Fi 에서 전송 p50 이 9ms 다. 대역폭은 지연이기도 하다.
- 첫 키프레임은 150~330ms(풀기 세션 만들기 약 100ms + 키프레임 압축 40~120ms). 붙을 때 한 번이다.

### 압축 시간이 바닥이다

루프백(같은 맥, 전송 0.2ms)에서 압축 설정을 바꿔 봤다. **합계의 대부분은 압축 17ms 다.**

| 바꾼 것 | 압축(SCK→압축 끝) p50 | 합계 p50 |
|---|---|---|
| 기본(3024×1964, 590만 화소) | 17.5ms | 21.9ms |
| `--scale 0.833`(2518×1636) | 13.2ms | 23.9ms |
| `--scale 0.667`(2018×1310) | 9.7ms | 14.2ms |
| `--scale 0.5`(1512×982) | 9.8ms | 13.2ms |
| H.264 | 16.4ms | 20.1ms |
| 저지연 모드 끔 | 15.8ms(p90 28.8) | 28.0ms |
| `--pix 420v`(BGRA→YUV 변환 없음) | 17.4ms | 21.4ms |
| `--fps 120` | 17.9ms | 23.6ms |
| RealTime 끔 · 장마다 `complete_frames` | 17.7~18.5ms | 25~32ms |
| 멈춘 동안에도 60fps 로 계속 압축 | 21.8ms | 26.2ms |

- 압축은 약 10ms 고정에 화소에 비례하는 몫이 붙는다. 0.667 배 아래로는 줄지 않는다. fps·RealTime·장마다 비우기·420v
  어느 것도 바닥을 못 내린다 — 하드웨어 인코더의 한 장 처리 시간으로 본다.
- 인코더는 한 장씩 처리한다. 멈춘 화면을 계속 압축하면 새 장이 앞 장을 기다려 오히려 느려진다(17.5 → 21.8ms).
- 저지연 모드를 끄면 p50 은 비슷해도 p90 이 튀고 장이 6~40배 커진다(작은 갱신에도 큰 장). 저지연 모드를 쓴다.
- 저지연 모드에서는 `MaxFrameDelayCount`·`PrioritizeEncodingSpeedOverQuality` 가 `-12900`(지원 안 함)이고
  `UsingHardwareAcceleratedVideoEncoder` 를 읽을 수 없다. 끄면 하드웨어로 읽힌다.

### 선명도 — 밝기(Y) PSNR

| 경우 | 전체 | 글자 많은 곳 |
|---|---|---|
| 실제 화면, 멈춤, 30Mbps | 52.0dB | 45.9dB(400×200, 2 배로 눈으로 봐도 빨간 코드 글씨까지 같다) |
| 스크롤 300 뒤 멈춤, 30Mbps, 다듬기 없음 | 32.9dB | 35.4dB(글자 상자 테두리·아이콘이 뭉갠다) |
| 같은 경우, 다듬기 10장(0.17초) | 48.1dB | 51.4dB |
| 같은 경우, 다듬기 30장(0.5초) | 51.9dB | 55.7dB |
| 같은 경우, 다듬기 60장 | 51.8dB | 55.5dB |
| 스크롤 300 뒤 멈춤, 60Mbps, 다듬기 없음 | 40.0dB | 44.6dB |
| 미니가 받기, 스크롤 300 뒤 멈춤, 30·60Mbps, 다듬기 30장 | 51.7·51.8dB | 55.1·56.0dB |

- 4:2:0 HEVC 로도 레티나 원래 해상도면 멈춘 화면은 원본과 구분이 안 된다. Parsec 도 mac 호스트는 4:2:0 이다(4:4:4 는
  Windows + NVIDIA/Intel 호스트에서만, Teams·Warp 요금제).
- **정지 화면 다듬기**: 움직이던 화면이 멈추면 SCK 는 새 장을 안 준다. 마지막 장은 움직일 때의 낮은 품질로 남는다.
  같은 장을 30장(60fps 로 0.5초) 더 압축하면 율 제어가 남는 비트로 품질을 올려 멈춘 화면 기준선까지 돌아온다.
  다듬기 장은 장마다 1~2KB 라 대역폭 부담이 없다. 계속 보내면(Parsec 의 Constant FPS) 위의 「멈춘 동안에도 계속 압축」처럼
  새 장의 지연이 늘어 30장에서 멈춘다.

### 재지 못한 것

- **눈에 닿기까지(유리→유리)**: 보는 쪽 화면 그리기·주사 시간. S1 의 네이티브 칸에서 잰다.
- **국내 중계 길**: 중계 서버에 EndpointId 허용 목록이 있어(`docs/kasanet.md` 「허용 목록」) 측정기의 임시 키로는 못 붙는다.
  재려면 측정기 id 를 중계 허용 목록에 잠깐 넣어야 한다. n0 공용 중계는 데이터 길이 아니라 재지 않았다.
- **다른 망 너머 직통**(인터넷 구멍 뚫기): 이번 직통은 같은 망이었다. 카사넷 P0 에서 다른 망 직통 왕복 6~8ms 를 쟀다.
- 영상·게임처럼 화면 전체가 새로 그려지는 실제 내용, 여러 화면, 폰 풀기, Windows.

## S1 로 가져갈 결정

- **HEVC · 저지연 모드 · 원래 해상도 · 30Mbps 기본**에 정지 화면 다듬기 30장. 빠른 망이면 60Mbps 로 올려 움직이는 동안의
  선명도(33 → 40dB)를 산다. 지연이 더 중요하면 0.667 배로 압축 8ms 를 아낀다(보는 쪽이 키워 그린다).
- 키프레임은 붙을 때와 풀기 실패 때만. 풀기 세션은 첫 키프레임에 만든다(약 100ms, 한 번).
- 직통에서는 장마다 신뢰 스트림으로 충분했다(손실 없음, p99 36ms). 손실 많은 길에서는 늦은 장을 버리고 키프레임을 청하는
  쪽으로 바꾼다 — 지금 압축은 매 장이 앞 장을 참조해 장을 버리면 다음 키프레임까지 화면이 깨진다.
- 보는 쪽은 웹 칸이 아니라 카사텀 칸 안에 네이티브로 그린다 — VT 가 내는 IOSurface 를 Metal 텍스처로 바로 쓴다(복사 없음).

## S1 — 카사텀 칸 안에서 보기 (2026-11-16)

### 흐름

```
보는 앱  Info 「화면 보기」 ─ machinescol.rs open_screen_mirror
  └ screen_stream::can_view(base)?  (이 판 macOS · 그 기기 /version kasanet.screen · 카사넷 직통·믿는 중계)
       ├ 아니면 → 지금 JPEG 웹 칸
       └ 맞으면 → open_screen_pane → ScreenView::open → kasa_remote::screen_stream::watch
                    kasanet::connect(base, "kasa/screen/1")  ── QUIC ──▶  그 기기 ScreenAccept → screen_stream::serve
                    풀기 일꾼(view.rs, VT) ◀── 장마다 단방향 스트림 ──  Host(host.rs): SCK 420v → VT HEVC
                    GUI(pane.rs paint): 새 장만 BGRA 로 GPU 에 올려 칸 본문에 비율 맞춰 그림
```

### 계약 (`kasa_remote::screen_stream`)

- 제어 스트림 `[u8 종류][u32 길이][내용]` — `P` 핑(보는 쪽 시계)·`p` 퐁(+보내는 쪽 시계)·`C` 설정 JSON·`I` 압축 정보 JSON·
  `K` 키프레임 청·`X` 거절 `{reason: permission|unavailable}`·`Q` 끝. 보는 쪽은 **핑 20번으로 시계를 맞춘 뒤** 설정을 보낸다.
- 장 `'F'` + seq·cap_id·key·t_cap·t_enc·가로·세로·파라미터 셋 + AVCC/HVCC NAL. 옛 장일수록 우선순위가 높다.
- 설정 `{codec, bitrate, fps, scale, refine, max_w, max_h}` — 보내는 쪽이 범위로 깎는다(1–200Mbps·1–120fps·0.25–1·다듬기 ≤240).
  기본은 S0 결정 그대로(HEVC 30Mbps 60fps 원래 해상도, 다듬기 30장).
- `max_w`·`max_h` 는 보는 기기의 가장 큰 모니터 픽셀 크기다(0 = 제한 없음). macOS 보내는 쪽은 장을 이 안에 들도록 줄여 뜬다 —
  3024×1964 를 그대로 H.264 로 누르면 압축 p50 18·p90 33·p99 59ms 인데, 3840×1600 모니터에 맞춘 2464×1600 은 8·12·22ms 다
  (2026-11-18, M 시리즈 맥북). 칸 크기가 아니라 모니터로 정한 까닭: 칸을 키우거나 꺼낼 때마다 다시 붙지 않게.
  Windows 복제는 원래 크기 그대로다.
- 못 보낸 장이 8장 쌓이면 다 버리고 키프레임부터 — 장마다 앞 장을 참조해 골라 버릴 수 없다. 보는 쪽은 풀기에 실패하면 키프레임을
  청하고 그 전 장은 버린다.
- 보내는 쪽은 거절 까닭을 쓰고 연결이 닫힐 때까지(최대 3초) 기다린다 — 바로 돌아가면 연결이 먼저 닫혀 보는 쪽은 「끊김」만 봤다
  (시험이 잡았다).
- 화면 기록 권한이 없으면 `permission` 을 알리고 연결마다 한 번 그 기기 앞에 권한 창을 띄운다. 칸에는 「그 기기 카사텀에 화면 기록
  권한이 없어요」.

### 칸

- `PaneContent::Screen { label, view_id }` 는 연 칸의 앞 탭이다. 연결·풀린 장은 `App.screen_views`(Workspace 는 PTY 스레드와
  공유라 실물을 못 둔다 — 웹 칸과 같은 까닭). `sync_screen_views` 가 루프마다 **창 트리에 실재하는 탭만** 연결을 쥐게 한다 —
  닫혀 되살리기 목록으로 물러난 탭은 연결을 버리고, 되살아나면 다시 붙는다.
- 재시작하면 화면 탭은 복원되지 않는다(세션 기록은 PTY 칸 기준이라 그 칸의 터미널만 남는다). 다시 연다.
- 조작은 S1b — 「조작」 단추를 켠 칸만 넣는다.
- 새 장은 풀기 일꾼이 `UserEvent::Redraw` 로 GUI 를 깨운다. GUI 는 그 장의 IOSurface 를 복사 없이 텍스처로 삼는다(S1c).
  못 하면 줄 간격 그대로 `Bgra8Unorm` 텍스처에 올린다(`GridRenderer::update_image_bgra`, RGBA 로 바꿔 담지 않는다).

### 실측 — 격리 앱 둘, 같은 맥(M3 Max), release

원본 리그 B 가 실제 화면(3024×1964)을 보내고 보는 리그 A 가 칸으로 본다. 카사넷은 루프백 직통(왕복 1ms).

| 경우 | 새 장 fps | 화면→풀림 p50 | GPU 올리기 | GUI 가 올린 장 |
|---|---|---|---|---|
| 실제 화면(거의 멈춤) | 1–3 | 21ms | 2.4ms | 새 장마다 |
| 검증 스크롤 8줄/장 | 60–61 | 21–22ms | 2.8–3.4ms | 초당 약 60 |
| 검증 스크롤 300줄/장 · 30Mbps | 60–61 | 21ms | 2.1–2.7ms | 초당 56–60 |

- 칸을 닫으면 보는 쪽 연결이 닫히고 보내는 쪽 뜨기·압축이 멈춘다(B CPU 6.6% → 2.3%, 스레드 52 → 48).
- 화면→풀림에는 GPU 올리기(약 3ms)와 화면에 내보내기가 빠져 있다. 600만 화소 장을 장마다 CPU 로 한 번 복사하는 값이라 S1b 에서
  IOSurface 를 Metal 텍스처로 바로 쓰면 없어진다.

### 리그

- 리그 포트는 실행마다 바뀌어 서로의 명부에 미리 못 적는다. 고정 포트 TCP 중계 둘(47821→A, 47822→B)을 먼저 띄우고 명부에는 그
  주소를 적는다 — 카사넷은 루프백 base 로 물은 `/version` 의 id 만 배우므로 중계를 거쳐도 그대로 배운다.
- 둘 다 `docs/verify-app.md` 격리 env + `KASATERM_KASANET_BIND=127.0.0.1:0`. B 는 화면 기록 권한이 있는 앱(카사텀 칸) 안에서 띄운다.
- A 에 `KASATERM_TEST_SCREEN_LABEL=<B 라벨>` 이면 직통이 선 뒤 화면 칸을 열고 2초마다 `[screen-view-test] … hud=60fps · 21ms · 직통
  upload=2.6ms uploads=N` 을 로그에 적는다(`testkit.rs run_pending_screen_view_test`).
- B 에 `KASATERM_TEST_SCREEN_SCROLL=<줄>` 이면 사람 화면을 건드리지 않고 마지막 화면을 장마다 밀어 60fps 로 움직이는 화면을 만든다
  (`screen_stream/scroll_probe.rs`, 검증 실행에서만).

### 남은 것

- 안 보이는 화면 탭(뒤 탭·다른 방)은 5초 뒤 연결을 닫고 다시 보이면 붙는다(`pane.rs HIDDEN_GRACE`). 리그에서 탭을 넘기자 보내는 쪽
  스레드가 54 → 51 로 줄고(뜨기·압축 멈춤), 탭을 다시 누르자 다시 붙어 45fps 가 들어왔다.
- 여러 화면(지금은 주 화면), 재시작 뒤 화면 탭 복원, 별도 창(aux)에서 화면 칸 그리기.
- Windows 보내기·보기(S3), 폰 보기(S2).

## S1b — 화면 칸에서 조작 (2026-11-16)

### 계약

- 제어 스트림에 둘을 더했다. `U` 조작 — 내용은 화면 거울과 **같은 JSON**(`{"t":"pointer",x,y,b,m}`·`scroll`·`key`·`text`,
  `docs/screen-mirror.md` 「조작」, 해석은 `screen_mirror::input_of`). `N` 조작 사정 `{ok, reason?}` — 바뀔 때만 한 번.
- `M` 커서 — 본문 1바이트(1 = 보는 쪽이 조작 중). 조작 중이면 macOS 보내는 쪽은 커서를 장에서 뺀다(SCK `showsCursor`). 보는
  쪽 자기 포인터가 곧 커서가 되어 영상 지연 없이 따라온다 — 장에 박힌 커서는 영상 지연만큼 늦게 따라와 굼떠 보였다(Parsec 도
  커서를 보는 쪽에서 그린다). Windows 복제는 원래 커서를 장에 넣지 않는다.
- 보내는 쪽 규칙도 화면 거울 그대로다 — 받은 차례대로 하나씩 넣고 기다린다, 연결이 쥔 직전 단추와 견줘 누름·뗌·끌기를 가른다,
  손쉬운 사용 권한이 없으면 연결마다 한 번 권한 창, **끊길 때 눌린 단추를 그 자리에서 뗀다**(시험이 이 줄을 빼면 실패한다).
- 조작은 세션이 뜨는 화면(`Session::display`, CGDirectDisplayID)에 넣는다. 뜨는 화면은 **주 화면**이다 — SCK 목록의 첫째가 주 화면이라는
  보장이 없어 `CGMainDisplayID` 로 고른다. 넣기는 앱의 `screen_input`(macOS CGEvent).

### 칸

- 칸 오른쪽 위 「조작」 단추로 켜고 끈다. 처음엔 보기만 한다 — 보다가 잘못 누르면 그 기기에서 일이 일어난다(폰·웹 보기와 같은 까닭).
- 조작 중이면: 장 위 누름·끌기·휠은 그 기기로(칸 밖으로 끌어 나가도 뗄 때까지 이어 보낸다 — 단추가 그 기기에 눌린 채 남지 않게),
  누르면 그 칸이 앞 칸이 된다. 좌표는 그린 장 사각형 안의 비율이라 받은 장 크기와 상관없다.
- 키: ⌘·⌃·⌥ 를 쥔 키와 이름 붙은 키(Enter·Tab·화살표·F키…)는 키로(`KeyboardEvent.code` = winit `KeyCode` 이름), 그 밖의 글은 글자째.
  한글은 이 앱이 macOS 에서 자모로 받아 조합하므로(`self.hangul`) **다 된 음절만** 보내고, 조합 중인 글은 칸 왼쪽 아래에 보여 준다.
  OS 입력기 확정 글(`Ime::Commit`)도 글자째.
- ⌘V 는 이 기기 클립보드 글을 그 기기에 글자째 넣는다(4000 바이트씩 끊어). 화면 탭이 앞이면 키·붙여넣기가 같은 칸 다른 탭 셸로 새지 않는다.
- ⌘W·⌘T·방 바꾸기 같은 앱 단축키는 그대로 이 앱이 먼저 받는다. ⌘C 는 그 기기로 가지 않는다(클립보드 맞추기는 S4).
- 그 기기에 손쉬운 사용 권한이 없으면 칸 아래에 「그 기기 카사텀에 손쉬운 사용 권한이 없어 조작을 못 넣어요」.

### 검증

- 규약 시험(`kasa-remote screen_stream`) — 조작이 세션 화면에 차례대로·끌기의 직전 단추·모르는 메시지 버리기·끊길 때 단추 떼기·
  사정은 바뀔 때만 한 번 / 권한 없음은 한 번 알리고 권한 창 한 번.
- 리그: 원본 B 에 `KASATERM_TEST_SCREEN_INPUT_LOG=<파일>` 이면 받은 조작을 **사람 화면에 넣지 않고** 파일에 적는다(검증 실행에서만).
  보는 A 에 `KASATERM_AUTOCLICKS="native:@<단추>;native:@<장 가운데>"`(커서를 옮겨 누르는 AppKit 길 — `x,y` 길은 커서 자리를
  안 옮겨 판정이 어긋난다) + `KASATERM_AUTOKEYS="…:text:ab;…:enter;…:cmd+a;…:text:ㅎㅏㄴ;…:enter"`. 단추·장 자리는
  `[screen-view-test] … toggle=… image=…` 로그로 먼저 읽는다.
- 결과(2026-11-16): 단추로 조작이 켜지고, 장 가운데 클릭이 `(0.497, 0.496)` 누름·뗌으로(계산값과 같다), `ab` 글자 둘·Enter·⌘A 가
  `KeyA`+command 로, 자모 `ㅎㅏㄴ` 이 「한」 한 글자로 주 화면(id 1)에 들어갔다.

## S1c — GPU 복사 없애기 (2026-11-16)

- 풀린 장은 VT 가 내준 IOSurface 기반 BGRA `CVPixelBuffer` 다. GUI 는 `CVPixelBufferGetIOSurface` 로 그 IOSurface 를 꺼내
  `MTLDevice newTextureWithDescriptor:iosurface:plane:` 로 Metal 텍스처를 만들고, `wgpu_hal::metal::Device::texture_from_raw` →
  `Device::create_texture_from_hal` 로 wgpu 텍스처에 감싸 그린다(`GridRenderer::set_image_iosurface`). 픽셀은 한 번도 CPU 를 안 지난다.
  `metal` 판은 wgpu-hal 28 이 쓰는 0.33 과 같아야 타입이 이어진다.
- 디코더는 다 쓴 버퍼를 풀에서 다시 쓴다. GPU 가 그리는 중에 같은 버퍼에 다음 장을 풀면 그리던 장이 바뀌므로 보기는 GPU 에 넘긴
  최근 장 3개(60fps 에서 50ms)를 쥐고 있는다(`view.rs HELD`).
- 텍스처를 못 만들면(다른 백엔드 등) 마지막 장을 CPU 로 한 번 올리는 S1 길로 물러난다.
- 실측(격리 앱 둘, release, 3024×1964, 검증 스크롤 300줄/장): GPU 올리기 장마다 **0.10–0.15ms**(CPU 복사 2.1–3.4ms), 60–61fps·
  화면→풀림 21–23ms 그대로, GUI 가 초당 약 60장. 색·글자는 원본대로 나왔다(창 캡처로 확인).

## S2 — 폰에서 보기 (2026-11-16)

### 길

- 폰은 이미 `/screen/ws` 로 JPEG 거울을 본다(직통이면 카사넷 포워드, 아니면 관문). 그 소켓에 **영상 방식**을 더했다 —
  `?codec=hevc&scale=0.667&mbps=15&fps=60` 을 실으면 데스크탑이 S1 과 같은 압축 세션(`screen_stream::Capture`)을 열고 장을 웹소켓
  바이너리 `'F'` 틀로 보낸다(`screen_stream::serve_ws`). 못 보낸 장이 쌓이면 버리고 키프레임부터 — 카사넷 장과 같은 규칙.
- 폰은 **카사넷 직통일 때만** 청한다(관문으로는 30Mbps 를 못 싣는다). 실제 소켓 주소로 가른다 — 앱이 돌아오면 늘 관문부터 붙어서
  「관문 깃발」로 가르면 직통이 서도 JPEG 에 머문다(시뮬레이터에서 걸렸다). 옛 판 데스크탑은 `codec` 을 모른 척 JPEG 를 보내고, 폰은
  `hello` 에 `codec` 이 없으니 JPEG 로 본다.
- 폰 화면보다 넉넉하게 2/3 크기(3024 폭 → 2018)·15Mbps 로 받는다 — 8배까지 키워 봐도 글자가 무르지 않고 셀룰러 직통에도 싣는다.

### 폰

- `lib/screen_video.dart` — `ScreenVideoSink`(실제는 iOS 네이티브, 시험은 가짜)와 장 머리 읽기. `screen_session.dart` 는 `hello` 의
  `codec` 으로 영상 방식에 들어가 받은 차례대로 장을 넘기고 크기·상태가 바뀔 때만 알린다(텍스처는 네이티브가 새 장마다 갱신한다).
  ack 는 없다. 화면은 `Texture(textureId)` — 확대·조작은 JPEG 와 같은 비율 상자 위에서 그대로 돈다.
- `ios/Runner/ScreenVideo.swift` — `FlutterTexture` + `VTDecompressionSession`(BGRA·IOSurface·Metal 호환 출력). 파라미터 셋이 셋이면
  HEVC, 둘이면 H.264. 풀기는 전용 큐에서. 장은 `BasicMessageChannel`(바이너리) 하나로 받는다 — 앞 8바이트가 텍스처 번호.
- **새 연결(리셋)은 장 채널 안의 `R` 한 바이트로** 보낸다. 메서드 채널로 따로 보내면 장과 차례가 엇갈려 첫 키프레임을 버린 채 기다릴
  수 있다. 키프레임을 기다리는 동안 일반 장이 오면 0.5초에 한 번 다시 청한다.
- 시뮬레이터·같은 맥 리그처럼 직통이 아닌 길에서 영상을 보려면 `--dart-define=KASA_SCREEN_VIDEO=always`.

### 검증

- 서버 시험(`kasa-remote screen_stream::tests::ws`) — 영상 소켓이 `hello`(codec·장 크기)를 먼저, 키프레임부터 순서대로 장을 보내고,
  `keyframe` 청·조작(`t:"input"` 사정)·닫으면 뜨기 멈춤·떠날 때 단추 떼기 / 압축 못 하는 판·권한 없음은 `denied`.
- 폰 시험(`test/screen_session_test.dart`) — 직통이면 `codec=hevc`·60fps 를 청하고, 장을 순서대로 넘기고 ack 를 안 보내며, 네이티브의
  키프레임 청을 그 기기로 / 옛 판은 JPEG 로 물러난다 / 텍스처가 없거나 관문이면 영상을 청하지 않는다.
- 시뮬레이터(아이폰, 디버그) — 검증 스크롤을 켠 원본 리그를 `KASA_ROOT` 로 두고 「PC 화면 조작」을 열자 상태줄 **60–61fps** 로
  영상이 텍스처에 그려졌다. 리그 소켓을 직접 열어 보면 `hello codec=hevc 2018×1310`, 3초에 180장·키프레임 1장.
- 남은 것: 실기(아이폰)의 셀룰러·Wi-Fi 직통 실측과 Ad Hoc 판. 안드로이드 풀기(MediaCodec)는 아직 없다 — 안드로이드는 JPEG 그대로.

## S3 — Windows 보내기·보기 (2026-11-16)

### 보내기 (`app/kasaterm/src/screen_stream/win.rs`)

- 뜨기는 DXGI 데스크톱 복제(주 화면, GPU 텍스처째), 압축은 Media Foundation 하드웨어 인코더 MFT(비동기 — NVENC·Quick Sync·AMF 가
  MFT 로 낸다)에 BGRA(ARGB32) D3D11 텍스처를 그대로 넣는다. 낮은 지연(`LowLatencyMode`·`LowDelayVBR`)·B 장 없음·키프레임은 청할
  때만(`GOPSize=0`). HEVC 인코더가 없으면 H.264 로 — 받는 쪽은 파라미터 셋 수로 코덱을 가른다.
- 인코더는 Annex-B 로 내고 화면 스트림 장은 4바이트 길이 머리 NAL + 따로 뗀 파라미터 셋이다 — `annexb.rs` 가 오간다.
- **새 장을 기다리는 동안 장치 잠금을 쥐지 않는다.** `AcquireNextFrame(16ms)` 로 기다리면 그 사이 인코더가 같은 장치를 못 써
  압축이 다음 장까지 밀린다 — 화면→압축 끝 p50 **58ms**. 0 으로 묻고 밖에서 1ms 쉬면 **7ms**(p90 8ms). 캡처 없이 고정 텍스처만
  넣어도 6.4ms 라 이것이 인코더 바닥이다(RTX 4070 Ti, 3840×1600, HEVC 30Mbps). NV12 로 바꿔 넣기·인코더 속성 바꾸기·
  일정 박자 넣기는 모두 37–75ms 로 원인이 아니었다.
- 주사율이 fps 보다 높은 모니터는 장을 fps 로 묶는다. 이른 장은 쥐어 두고 다듬기가 한 간격 뒤에 보내 마지막 화면을 놓치지 않는다.
- **복제는 프로세스에 하나** — 같은 출력을 두 번 `DuplicateOutput` 하면 E_INVALIDARG 라 두 번째 보기(맥 칸과 폰)가 거절됐다.
  복제 하나(`Desktop`)를 보기들이 나눠 쓰고 fps·다듬기만 보기마다 센다. 마지막 보기가 떠나면 닫힌다.
- 조작은 화면 거울과 같은 `screen_input`(주 화면 번호)으로 넣는다. 복제에는 마우스 커서가 없다.

### 보기 (`win_view.rs`, 보는 칸은 `view.rs` 를 macOS 와 같이 쓴다)

- 보내는 쪽에 **H.264** 를 청한다 — Windows 의 HEVC 풀기는 스토어 「HEVC 비디오 확장」이 있어야 해서 기기마다 다르다.
- MF H.264 디코더(동기 MFT, D3D11 장치 관리자를 줘 하드웨어로, `MF_LOW_LATENCY`)가 NV12 텍스처 배열 한 칸을 낸다. 비디오
  프로세서가 그것을 화면 크기 BGRA **공유 텍스처**(NT 핸들, 6칸 고리)로 옮기고(부호화 크기의 16 배수 덧줄을 잘라 낸다 —
  1964 → 1968), 끝 알림 질의로 GPU 가 다 쓴 뒤에 넘긴다.
- 칸(wgpu·Vulkan)은 그 핸들을 `texture_from_d3d11_shared_handle` 로 들여와 복사 없이 그린다(`GpuRenderer::set_image_d3d11`).
  고리 칸마다 한 번 들여와 다시 쓴다. 기기가 `VULKAN_EXTERNAL_MEMORY_WIN32` 를 지원할 때만 장치에 그 기능을 청한다.
- 들여오기를 못 하는 기기(확장 없음·GPU 가 다름)면 그때부터 CPU 로 읽어 올린다. 3024×1964 한 장 읽어 내기가 장당 14ms
  (Map 10.7·복사 3.6, 풀기·변환은 0.4ms)라 기본 길로는 쓰지 않는다.

### 검증

- 같은 PC 격리 앱 둘(보내기·보기, 디버그 빌드, RTX 4070 Ti, 3840×1600 H.264): 공유 텍스처 길로 칸에서 **59–60fps·화면→풀림
  6–7ms**, GUI 올리기 0.01ms(`zero_copy=true`). CPU 로 읽어 올리던 첫 판은 50–54fps·42–52ms·올리기 9ms 였다. 그 사이 맥에서 같은
  보내기 앱의 웹소켓을 열어 HEVC·H.264 를 받아 보니(두 번째 보기) 둘 다 끊기지 않았다 — 받은 장 177·178장을 VideoToolbox 가
  모두 풀었고 색·글자도 원본대로였다.
- 장 덤프 시험 `win_view::tests::decodes_a_frame_dump`(ignored, `KASATERM_TEST_SCREEN_FRAMES=<덤프>`) — 맥이 보낸 H.264
  3024×1964 179장을 Windows 디코더가 모두 풀었고 크기는 잘라 낸 그대로다. 덤프는 `/screen/ws?codec=h264` 의 바이너리 장을
  `[u32 길이][장]` 으로 이어 적은 것이다.
  첫 장 뒤 장당 **2.3ms**(풀기·변환·GPU 끝 기다림, 공유 텍스처 길) — CPU 로 읽어 내는 길은 13.4ms.
  CPU 길로 적은 마지막 장을 맥의 ffmpeg 풀기와 견주면 PSNR 42dB 로 색·글자가 눈으로 같다(색 공간 BT.709·16–235 확인).
- 맥 칸에서 Windows 화면 보기는 리그로 재지 못했다 — 두 기기 리그 사이 카사넷 직통을 세우려면 Windows 리그가 루프백 밖 UDP 를
  열어야 하고, 새 exe 는 사람 화면에 방화벽 창을 띄운다. 비트스트림은 위 VideoToolbox 풀기로, 칸은 S1 그대로라 실기 판에서 본다.

### 리그 (Windows, 같은 PC 둘)

- 카사넷은 `127.0.0.1` base 로 물은 `/version` 의 id 만 배운다. 리그 둘을 `KASATERM_BIND=127.0.0.2`·`127.0.0.3` 에 열고
  (사용자 앱의 `127.0.0.1`·`0.0.0.0` 8765 와 겹치지 않는다) `127.0.0.1` 의 고정 포트 TCP 중계 둘을 그 앞에 두고 명부에 적는다.
  보내는 쪽 명부에도 보는 쪽을 적어야 화면 입구가 받는다.
- **중계는 두 리그가 다 뜬 뒤에 연다.** 리그가 아직(또는 이미) 없을 때 `127.0.0.x:8765` 는 사용자 앱(`0.0.0.0:8765`)이 받아,
  명부 폴링이 사용자 앱의 카사넷 id 를 배우고 그쪽에 붙으려다 시간 초과로 끝난다 — 그 뒤 진짜 리그는 「unknown endpoint」로
  거절된다. 리그를 거둘 때도 중계를 먼저 끈다.
- `.cmd` 리그 스크립트는 ASCII 로만 — 한글 주석이 CP949 로 읽혀 깨진 조각이 명령으로 실행되고 `<`·`>` 가 섞이면 스크립트가
  중간에 멈춘다. 같은 cmd 에서 띄운 앞 리그의 `set` 이 남으니 `setlocal` 로 시작한다.
- 루프백 리그(`KASATERM_KASANET_BIND` 가 루프백)는 공유기 UPnP 매핑·정리를 하지 않는다 — 그것이 `0.0.0.0` UDP 를 열어 Windows
  방화벽 창을 띄웠다(2026-11-16).

### 남은 것

- 맥 칸에서 Windows 화면·Windows 칸에서 맥 화면을 실기 판으로 보고 지연을 잰다. 마우스 커서 그리기(복제에 없다), 여러 화면.

## S3b — Windows 보안 데스크톱까지 (2026-11-16)

UAC 확인 창·잠금 화면은 Windows 가 보안 데스크톱(Winlogon)에 띄운다. 사용자 프로세스는 그 데스크톱을 열 수 없어 복제가
끊기고(JPEG 거울은 까만 화면) SendInput 도 막힌다. 그래서 Parsec 과 같은 꼴로 간다 — 집 PC 의 Parsec 을 들여다보면
`pservice.exe`(LocalSystem 서비스, 세션 0) → `parsecd.exe`(**SYSTEM, 사용자 세션**) → `parsecd.exe`(사용자, IPC 로 잇는다)다.

- 서비스 `KasatermScreen`(설치기가 건다, `kasaterm.exe --screen-service`) — 자기 SYSTEM 토큰을 복제해 세션 번호만 지금 콘솔
  세션으로 바꿔 도우미(`kasaterm.exe --screen-agent`)를 띄운다. 세션이 바뀌면 옮겨 띄우고, 죽으면 1–30초 물러서며 다시
  띄운다. 잡 오브젝트(닫히면 죽임)라 서비스가 어떻게 끝나도 도우미가 남지 않는다. 기록은 `%ProgramData%\kasaterm\screen-service.log`.
- 도우미(`win_agent.rs`)는 S3 의 뜨기·압축(`win::start_local`)과 조작(`screen_input`)을 그대로 쓴다. 다른 점은 뜨기·조작 스레드가
  입력 데스크톱을 따라간다는 것 — 복제가 `DXGI_ERROR_ACCESS_LOST`(UAC 에서 돌아올 때는 `DXGI_ERROR_INVALID_CALL` 도 온다)로
  끊기면 `OpenInputDesktop`·`SetThreadDesktop` 으로 그 데스크톱에 옮겨 다시 연다. 앱이 직접 뜰 때도 같은 길이지만 Winlogon 을
  못 열어 돌아올 때까지 기다린다(전에는 끊겼다).
- **뜨기는 데스크톱마다 새 스레드**다. DXGI 를 한 번 쓴 스레드는 `SetThreadDesktop` 으로 Winlogon 에 못 옮겨, 조작은 들어가는데
  화면은 UAC 동안 한 장도 안 나왔다.
- **새 복제의 첫 장은 버리지 않는다.** 멈춘 UAC 화면의 첫 장은 마우스 변화만 있는 장(`LastPresentTime` 0)으로 온다 — 바뀐 장만
  보내던 규칙으로 버리면 다음 변화가 없어 보는 쪽은 마우스를 움직일 때까지 그 화면을 못 봤다.
- 앱은 세션 파이프 `\\.\pipe\kasaterm-screen-<세션>` 으로 붙는다. 도우미가 없으면(서비스 없는 설치·옛 판) 앱이 직접 뜬다.
  장 시각은 두 프로세스가 같이 읽는 QPC 로 찍는다(`Instant` 는 프로세스마다 기점이 다르다).
- 연결 하나는 한 방향으로만 흐른다 — 장 연결(앱 `S` 설정 → 도우미 `N`·`F`·1초 `H`)과 조작 연결(앱 `C` → `K`·`I`). 동기 파이프
  핸들은 읽기가 막혀 있는 동안 같은 핸들의 쓰기도 막혀서다. 숨(`H`)으로 앱이 떠난 것을 도우미가 1초 안에 안다.

### 막아 둔 것

- 서비스·도우미도 `kasaterm.exe` 다. 이름·경로로 앱을 세는 곳은 `--screen-service`·`--screen-agent` 를 빼야 한다 — 그러지 않으면
  「이미 떠 있다」로 읽는다. 재시작·업데이트 도우미(PowerShell)는 `app_restart::ps_running_fn` 으로 명령줄까지 보고 뺀다(관리자 권한
  도우미에서 옛 경로 비교가 서비스·도우미를 세어 「다른 인스턴스」로 설치를 멈출 수 있었다 — 집 PC 실측 3개 → 1개). 로그인 자동 실행
  스크립트처럼 기기에 따로 둔 것도 같다(집 PC `autostart-restore.vbs` 가 서비스를 앱으로 세어 로그인 때 앱을 안 띄웠다).

- 파이프 DACL 은 SYSTEM 과 그 세션 사용자뿐, 원격 클라이언트는 거절. 도우미는 붙은 프로세스가, 앱은 파이프를 연 프로세스가
  같은 kasaterm.exe(설치판은 관리자만 쓰는 Program Files)인지 본다. 이름을 먼저 차지한 프로그램이 있으면 도우미는 물러난다.
- 남는 위험은 Parsec 과 같다 — 사용자 권한으로 도는 악성 코드가 그 kasaterm 프로세스를 조종하면 UAC 「예」를 누를 수 있다.
  원격 쪽은 기존 화면 거울과 같은 인증(카사넷 허용 기기)만 통과한다.

### 검증 (집 PC, 디버그 판)

- 시험 서비스: 관리자 ssh 에서 `sc.exe create KasatermScreenTest binPath= "\"<리그 exe>\" --screen-service" obj= LocalSystem`
  → `sc.exe start`. 서비스 SYSTEM·세션 0 → 도우미 **SYSTEM·세션 1** → 파이프 `kasaterm-screen-1`(Parsec 과 같은 꼴). 사용자 쓰기
  폴더의 exe 를 SYSTEM 으로 돌리는 셈이라 시험 뒤 바로 `sc.exe delete` 한다. 리그 exe 가 도우미와 같은 파일이어야 붙는다.
- 리그 웹소켓으로 받는 중에 `Start-Process cmd -Verb RunAs` 로 UAC 창을 띄우자 장에 UAC 창이 그대로 실렸고(`info.agent=true`),
  웹소켓으로 보낸 `Escape` 가 그 창을 닫았다(consent.exe 1 → 0). 돌아온 뒤에도 끊기지 않고 60fps 로 이어졌다.
- 잠금 화면은 사람 화면을 잠그게 되어 재지 않았다 — 같은 Winlogon 데스크톱이라 같은 길을 탄다.
- **멈춘 화면에서는 데스크톱이 바뀐 것을 복제가 늦게 안다**(2026-11-18 집 PC 설치판). 보는 중에 UAC 창이 뜨면 복제는
  `ACCESS_LOST` 를 다음 화면 변화(마우스 움직임)에야 알려, 보는 쪽은 그 전 데스크톱을 계속 봤다 — 실측: UAC 가 뜬 뒤 8초 넘게
  옛 화면, 첫 조작이 들어간 순간(11.7초) 그제야 UAC 화면. 누름 자체는 그때도 들어갔다(「아니요」 누름으로 consent.exe 1 → 0)
  — 사람은 안 보이는 창을 누르던 셈이다. 그래서 뜨기 스레드가 250ms 마다 입력 데스크톱 이름을 자기 데스크톱과 견주고
  (`win.rs input_desktop_moved`), 다르면 그 데스크톱에서 다시 뜬다. Winlogon 을 못 여는 사용자 앱은 연 적이 있을 때만 떠난 것으로
  본다(못 여는 채로 다시 뜨면 헛돈다).
- 집 PC 재현은 앱의 `/screen/ws?codec=h264` 를 ssh 포워드(루프백)로 받아 장을 ffmpeg 로 풀고, 같은 소켓에 조작 JSON 을 보낸다 —
  도우미 파이프는 같은 kasaterm.exe 만 받아 다른 시험 프로그램으로는 못 붙는다.

## 화면 칸만 · 별도 창 (2026-11-16)

- PC 의 「화면 보기」(옛 「화면 거울」)는 화면 칸으로만 연다. 그 기기가 옛 판이거나 직통이 아닐 때 JPEG 웹 칸으로 물러나던 길과 그 보기 페이지
  (`/screen`, `assets/screen/index.html`)는 느려 걷어냈다(`/screen/ws` 는 폰이 쓴다). 대신 칸이 까닭(「카사넷 직통을 기다리는 중」·
  「그 기기 카사텀이 화면 스트림을 모르는 판」)을 띄우고, 보이는 동안 연결이 닫혀 있으면 3초마다 다시 붙는다(`pane.rs RETRY_AFTER`).
- ⋮ 「별도 창으로」가 화면 탭을 별도 OS 창(`window.rs ScreenWindow`)으로 꺼낸다. 탭만 칸에서 빠지고 보기·연결은 `screen_views` 에
  그대로라 끊기지 않는다. 보기는 그려진 창(`Surface`)을 기억해 누름은 그 창 것만 받고, 창을 옮긴 직후 그 창 렌더러에 장이 없으면
  멈춘 화면이라도 마지막 장을 다시 올린다. 본창은 본창 보기의 새 장에만 다시 그리고, 꺼낸 창은 제 보기의 새 장에만 다시 그린다.
- 검증(격리 앱 둘, 같은 맥, 디버그): `KASATERM_TEST_SCREEN_POPOUT=8` 로 첫 장 뒤 꺼냈다가 8초 뒤 되돌렸다 — 꺼낸 창에서 60–61fps·
  21–22ms·복사 없음(올리기 0.25ms), 되돌린 칸에서도 그대로. `KASATERM_TEST_SCREEN_ANYPATH=1` 로 직통이 서기 전에 열자 「카사넷 직통을
  기다리는 중」을 띄우다가 직통이 선 뒤 스스로 붙어 60fps 로 받았다.
