# 기기 사이 Claude 계정 선택

접근 토큰의 갱신·401 복구는 [agent-chains.md](agent-chains.md), 사람이 고른 계정을 다른 기기에
반영하는 규칙은 이 문서가 정본이다. 401이 났다는 이유로 다른 계정으로 임의 전환하지 않는다.

## 신원과 슬롯

- 슬롯 번호와 별명은 기기마다 다르다. 신원은 해당 슬롯의 토큰으로 조회한 프로필의 **계정 UUID와 조직 UUID 쌍**이다.
  공유 `claude auth status` 캐시, 별명, 기본 슬롯 번호로 대신하지 않는다.
- 표시용으로 남겨 둔 옛 신원은 전환 근거로 쓰지 않는다. 확인되지 않으면 기존 선택을 유지하고
  `account_sync_identity_unverified`로 거절한다.
- 이메일·조직은 설명에만 쓰며 앞뒤 공백만 제거한다. 공급자 규칙을 확인하지 않은 대소문자 변환은 하지 않는다.
  UUID는 유효한 nil 아닌 값만 받으며, 같은 UUID의 이메일·조직 표시명이 바뀌어도 같은 신원이다.
- 프로필 캐시는 경로가 아니라 실제 요청에 쓴 접근 토큰에 묶인다. 앱의 표시 캐시는 후보를 찾는 힌트뿐이다.
  작업대에 쓸 실제 자격과 이미 활성이라 남길 자격을 모두 토큰별 프로필 증명과 대조하고, 적용 뒤와 ACK 직전에도
  다시 확인한다. 새 토큰의 증명이 아직 없으면 거절하고 백그라운드 신원 재확인을 요청한다. 원문 토큰과 지문은 로그에 남기지 않는다.
- 활성 행의 표시 조회는 작업대를 볼 수 있지만 그 결과는 화면에만 쓴다. 슬롯 신원 표(`claude_account_emails`·`_orgs`,
  statusline·관문 계정 목록·관문 받기의 후보가 읽는다)에는 그 슬롯 금고의 답이나, 작업대 소유 표식이 같은 슬롯·같은
  UUID 로 적어 둔 작업대의 답만 남긴다. 동기화 후보는 슬롯 금고 조회로만 채운다. 외부 `/login`이 작업대를 바꿨다는
  이유로 예전 슬롯에 새 신원을 붙여 고르지 않는다. 후보 조회는 슬롯별 한 개의 백그라운드 요청으로 제한한다.
- 신원 증명은 토큰의 현재 유효성을 보증하지 않는다. 전환·성공 응답용 증명 조회는 `expiresAt`이 현재 시각을 지난
  자격을 거절한다. 아직 만료 전인 토큰의 공급자 측 폐기까지 이 검사만으로 알아내지는 못한다.
- 일치하는 슬롯이 하나면 그 슬롯, 여러 개면 **일치하는 신원 안에서만** 보낸 별명이 유일한 슬롯을 고른다.
  애매하면 `account_sync_ambiguous`, 같은 신원이 없으면 `account_sync_missing`이다.
  다른 신원에 같은 별명이 있어도 선택하지 않는다. 미선택 슬롯(`id=""`)은 후보가 아니다.

## 작업대에서 금고로 되저장

작업대의 바이트가 달라졌다고 곧바로 같은 계정의 토큰 갱신으로 해석하지 않는다. 외부 `/login`으로 다른 계정이
들어온 것일 수 있다. 현재 자격의 토큰별 UUID 증명이 작업대 소유 표식 및 금고 신원과 일치할 때만 되저장한다.
증명이 없으면 보류하며, 새 프로필 확인 뒤 다음 주기에서 다시 확인한다. 기존 금고가 소유 표식에 적힌 바이트와
동일하면 표식의 UUID를 쓸 수 있어 옛 접근 토큰의 증명 TTL이 끝나도 새 갱신을 안전하게 되받는다.
되저장은 안전한 무변경·보관 완료·보류를 구분한다. 보류를 단순한 무변경으로 취급해 다른 계정으로 덮지 않는다.
새 갱신 자격의 신원이 아직 확인되지 않았다면 작업대와 예전 금고를 모두 보존한다. 재조회는 목표 금고뿐 아니라
떠나는 계정의 실제 작업대를 먼저 조회하며, 증명이 채워진 뒤 사람이 다시 선택했을 때 보관을 마치고 전환한다.

소유 표식의 UUID는 선택 필드다. 옛 표식은 정확히 같은 작업대 바이트가 유지되는 동안 새 증명이 생기면 보강한다.
현재 자격·금고·표식을 쓰기 전에 다시 대조하고, 앱의 전환과 되저장 작업은 같은 잠금으로 직렬화한다.
자격 쓰기가 성공하면 소유 표식을 먼저 갱신한 뒤 최종 증명을 검사한다. 마지막 확인이 실패했다고 예전 소유자를
남기면 다음 주기에 새 계정 자격을 예전 금고에 복사하게 된다.

같은 슬롯을 명시적으로 다시 고르더라도 현재의 다른 계정 자격이 유일한 사본이면 버리지 않는다.
작업대가 외부 로그인으로 바뀐 경우, 계정 화면에서 그 계정을 추가·로그인하고 그 슬롯을 먼저 선택하도록 안내한다.
명시적으로 고른 목표 슬롯과 작업대의 실제 UUID가 모두 일치할 때만 그 슬롯에 현재 자격을 보관하거나 이미 보관된
더 최신의 같은 계정 자격을 확인한다. 무작위 슬롯 검색·미분류 자격 보관함은 만들지 않는다.
소유 표식이 없거나 비어 있어도 이 명시 복구를 쓸 수 있다. 예전 기본 로그인 백업에 다른 자격이 있으면 그대로
보존하고, 실제 작업대 신원을 먼저 조회해 직접 고른 같은 UUID의 슬롯만 사용한다. 작업대 조회 결과로 슬롯 후보를 만들지는 않는다.
저장 성공을 확인하기 전에는 작업대를 덮거나 소유 표식·ACK를 바꾸지 않는다. 배경 맞추기는 이 명시 복구를 하지 않는다.
증명이 없는 부팅에서는 안전하게 보존된 무변경 상태를 유지하며, 보관 판정을 한 뒤 작업대가 다시 바뀌면 전환을 보류한다.

## 공유 선택 — 관문 공통 설정의 순서 있는 선택

모든 기기가 같은 계정으로 모이는 정본은 관문 공통 설정(`/relay/account-sync`)의 opt-in 키
`claude_account_choice` 다(`kasa_mcp::account_sync::choice`). 값은 공급자 **계정·조직 UUID**, 표시·사슬 탐색용
이메일·조직명, `intent`(선택마다 새 UUID), `base`, `after`, 관문이 찍는 `rev` 뿐이다. 슬롯 번호·별명·토큰·지문은
싣지 않는다. UUID 만 권위이고 이메일·조직명은 힌트다.

- **순서는 관문 revision 이다. 기기 시계는 쓰지 않는다.** 기기는 `rev` 없는 intent 를 쓰고, 그때 본 스냅숏
  revision 을 `base` 로 고정한다. 관문은 커밋하면서 `rev` 를 찍고, 지금 정본의 `rev` 가 `base` 보다 크면(그
  선택을 못 보고 고른 것이면) 409 로 거절한다. 그래서 오래 오프라인이던 기기의 선택·지연 응답·409 뒤 재적용이
  새 선택을 되돌리지 못한다. 일반 설정은 예전처럼 rebase 되고 선택만 이 규칙을 따른다. 시계가 틀린 기기, 관문이
  모르는 revision 을 `base` 로 든 값은 순서를 앞당기지 못한다.
- **자기 전송 위로만 이어진다.** 동기화는 intent 를 보내기 직전, 새 선택과 같은 잠금 안에서 그 값이 아직 로컬
  값일 때만 로컬 전용 `claude_account_choice_sent` 에 적는다(최근 8개). 새 intent 의 `after` 는 이 목록 — 보냈지만
  답을 못 본 자기 intent 들 — 이고, 관문은 정본이 그중 하나면 `base` 가 낮아도 받는다. 전송 중에 몇 번을 더 골라도
  (같은 계정 재선택 포함) 마지막 선택이 산다. 보내지 않은 중간 선택은 관문에 있을 수 없어 목록에 넣지 않는다.
  ACK 는 값 비교가 아니라 `intent` 로 그 intent 만 소비한다.
- **선택은 KASA 계정에 묶인다.** 로컬 전용 `claude_account_choice_owner` 에 그 값을 쓴 KASA 계정(관문 주소+계정의
  해시)을 둔다. 다른 KASA 계정으로 로그인한 동기화는 옛 값을 보내지도 따르지도 않고 지운다. 신원 증명을 기다리는
  앱의 선택도 고를 때의 KASA 계정·로그인 세대·선택 세대에 묶여, 하나라도 바뀌면 버린다.
- **정본은 값 비교가 아니라 계획으로 맞춘다.** 원격이 A→B→A 로 돌아와 이전 값과 같아 보여도 거절된 로컬 intent 는
  원격 정본으로 바뀐다. 관문에 값이 없으면(옛 관문·아직 아무도 안 고름) 로컬 값을 지우지 않는다.

### 무엇이 선택을 내나

사람의 선택(같은 슬롯 재선택 포함)과 자동 한도 전환만 낸다. 신원이 증명된 뒤에 내며, 증명을 기다리면 고를 때의
revision 으로 나중에 낸다. 다른 기기를 따라 바꾼 것은 다시 내지 않는다.

**구판→신판 이행 규칙**: 업데이트·부팅·첫 바인딩·옛 관문 400 어느 것도 기기의 현재 선택(`claude_account`)을
새 intent 로 올리지 않는다. 어느 기기가 먼저 켜졌는지로 정본을 정하지 않는다. 정본은 이행 뒤 사람이 한 번 명시적으로
고를 때 처음 생긴다. 옛 관문은 이 키를 400 으로 거절하고, 그때 intent 는 고른 그대로(같은 `intent`·`base`) 로컬에
남고 나머지 설정만 동기화된다 — 다시 찍어 새 intent 로 만들지 않는다.

### 따라가기

동기화 주기(15초, 재연결·부팅 포함)마다 관문 응답을 적용한 뒤 GUI 가 정본을 본다.

1. 고른 슬롯의 금고 신원과 **작업대의 실제 신원**이 둘 다 정본 UUID 면 끝이다. 작업대 신원은 동기화 스레드가 재
   둔다(키체인 읽기는 자식 프로세스라 GUI 스레드에서 하지 않는다). 바깥 `/login` 으로 작업대만 다르면 같은 슬롯을
   다시 골라 위의 보존·검증을 타고, 사람이 풀어야 하는 경우(유일한 다른 로그인 보존 등)는 안내를 띄운 뒤 새 정본이
   올 때까지 같은 시도를 되풀이하지 않는다.
2. 같은 UUID 의 슬롯이 있으면 그 슬롯을 검증 전환으로 고른다. 여럿이면 같은 계정이라 목록 앞의 것을 고른다.
3. 증명이 아직 없는 슬롯이 있으면 몇 주기 기다린다(「확인 중」 안내).
4. 없으면 관문이 그 계정 사슬을 정상으로 쥐고 있을 때만 공식 받기 길(`adopt_held_claude_chain` →
   `agent_chains::adopt`, 「다른 기기에 있는 계정」 받기와 같은 길)로 새 슬롯을 준비한다. 확인된 다른 계정 슬롯은
   건드리지 않는다. 받은 토큰의 UUID 가 정본과 같아야 고르고, 다르면 고르지 않고 알린다. 사슬이 없거나
   `reconnect_required` 면 「이 기기에서 로그인 필요」를 보인다.

따라 바꾼 뒤 5분은 자동 한도 전환이 쉰다. 자동 전환은 판단을 시작할 때의 선택 세대에 묶여, 그 사이 사람이 고르거나
따라 바뀌었으면 옛 사용량으로 옮기지 않는다. 기기마다 전환 기준(%)이 다르면 기준이 가장 낮은 기기가 공유 선택을
먼저 옮긴다.

계정 메뉴의 안내는 지금 따라가는 정본의 상태가 지난 P2P 전송 결과보다 먼저다. 새 정본이 오면 다른 계정을 보낸
지난 P2P 결과는 걷는다.

## 요청과 확인

새 요청은 `/settings/action`의 `claude-account-sync-v1`이다. `id`는 UUID 쌍·이메일·조직 JSON의 URL-safe
base64이며, `label`은 보낸 기기에서 사람이 붙인 별명이다. 자격증명이나 토큰 지문은 보내지 않는다.
성공 응답은 `ok=true`와 요청과 정확히 같은 `account_sync_identity`를 반환해야 한다.

순서 있는 선택이 있는 기기(정본이든 낼 intent 든)는 `claude-account-sync-v1` 을 그 선택과 같은 UUID 일 때만
적용한다. 다르면 적용하지 않고 동기화를 깨워 `account_sync_ordered` 로 답한다 — 늦게 도착한 옛 P2P 요청이 관문
순서를 우회해 새 선택을 되돌리지 못하게. 보낸 기기는 이 답을 「관문 정본 확인 대기」로 보이고 완료로 세지 않는다.
선택이 없는 기기(옛 관문)만 예전처럼 적용한다.

옛 `claude-account-identity`는 이메일 또는 조직명 하나만 보내 둘을 함께 증명하지 못한다.
새 수신기는 이 요청을 `account_sync_update_needed`로 거절한다. 새 송신기는 구형 서버의
`action_unknown`을 업데이트 필요로 표시하며 옛 요청으로 폴백하지 않는다.

선택한 슬롯과 같은 슬롯을 다시 골라도 작업대를 확인하고 기기 전파를 다시 실행한다.
로컬 적용 성공과 기기별 결과는 별개다. 결과 토스트에는 각 기기의 완료·중복 계정·계정 없음·신원 확인 필요·
로그인 확인 필요·업데이트 필요·응답 확인 실패를 구분해 표시한다. 원격의 오류 본문은 출력하지 않고
알려진 오류 코드만 읽는다. 응답을 잃으면 적용됐는지 단정하지 않는다.

## 순서와 재시도

- 발송 워커는 하나다. 아직 보내지 않은 선택은 최신 것 하나만 남긴다.
- 로컬의 새 선택 또는 수신한 선택이 성공하거나 슬롯을 삭제·재로그인하면 이전 발송 대기와 이전 결과 알림을 취소한다.
- 각 기기에 보내기 직전과 응답 직후 요청 순번·KASA 로그인 세대를 확인한다. 늦게 온 결과는
  현재 선택 슬롯과 순번이 모두 맞아야 화면에 뜬다. A → B → A에도 이전 A의 결과를 쓰지 않는다.
  보내기 직전에 현재 작업대의 토큰 증명도 다시 대조하므로, 외부 로그인으로 자격만 바뀐 경우에도 이전 신원을 보내지 않는다.
- P2P 실패를 영구 큐에 남겨 자동 재시도하지 않는다. 다른 기기의 더 최근 수동 선택을 예전 요청이 덮을 수 있기
  때문이다. 오프라인 기기의 수렴은 위 공유 선택이 맡는다 — 다시 붙으면 다음 동기화 주기에 정본을 따른다.
- 이미 네트워크로 보낸 요청은 수신기의 처리까지 취소할 수 없다. 기기 여러 대에서 동시에 서로 다른
  선택을 하면 전역 순서는 보장하지 않는다. 토스트가 보장하는 것은 해당 요청의 응답 시점의 결과다.

## 검증과 복구

공유 선택·사슬 받기는 실제 관문 라우터에 기기 둘을 붙인 리그(`gateway_agent_chains/recovery_rig.rs`)와
`account_sync` 경합 시험(오프라인 r10→원격 r11→재접속·재부팅, GET/PATCH 사이 409, 원격 A→B→A, 늦은 ACK+새
수동 선택+오래된 자동 판단, 전송 중 연속 선택, 첫 바인딩·옛 관문 400, 다른 KASA 로그인)으로 검증한다. 가짜
공급자·메모리 저장소만 쓴다. 앱 격리 실행은 신원 조회·키체인 경로가 꺼지는 설계라 이 수렴을 돌리지 않는다.

한 기기의 슬롯이 다른 계정으로 묶였을 때(예: 별명은 개인 계정인데 금고가 Gmail) 그 슬롯을 손으로 고치지 않는다.
새 판·새 관문이 깔린 뒤 정상 계정이 든 기기에서 그 슬롯을 **한 번 명시적으로 다시 고르면** 정본이 생기고, 다른
기기는 같은 UUID 의 슬롯이 없으니 관문의 정상 사슬을 새 슬롯에 받아 UUID 를 확인한 뒤 고른다. 잘못 묶인 슬롯과
기존 Gmail 슬롯은 그대로 남으니, 원하면 그 뒤 계정 화면에서 정리한다.

`cfg(test)`와 검증·격리 환경에서는 실제 기기 전파가 꺼진다. 회귀 시험은 가짜 슬롯·전송 함수·loopback
HTTP 서버만 사용한다. 운영 계정, 키체인, 실제 기기의 선택은 검증 과정에서 변경하지 않는다.
