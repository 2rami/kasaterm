# 긴 잡

오래 실행되는 빌드·시험·서버를 시작할 때만 읽는다. 짧게 끝나는 조회·검사는 현재 도구에서 실행하며 이 절차를 적용하지 않는다. 읽기 전용 상태·완료 감시도 새 셸 칸 없이 백그라운드 감시로 둔다.

1. 실행별 새 로그 폴더를 정하고 실제 명령·작업 경로를 고정한다. 카사텀 안에서는 새 작업용 셸 칸에 실행하고, 밖에서는 사용 가능한 백그라운드 잡 도구를 쓴다.
2. stdout·stderr를 로그에 남기고 실제 종료 코드를 기록한다. 파이프를 쓰면 `pipefail` 또는 원래 명령의 종료 코드를 보존한다. 실패 뒤의 `echo`가 성공을 대신하지 않게 한다.
3. 카사텀의 새 셸은 `split` 응답 ID로 지정한다. 명령을 준비한 스크립트를 실행하고 종료 뒤 셸을 끝낸다. 실행 중인 학생 입력창에 셸 명령을 보내지 않는다.
4. 성공·실패 때 끝나는 별도 감시를 둔다. 진행·오류·끊김 등 변경분과 필요한 로그 꼬리만 읽는다. 같은 전체 로그나 상태를 계속 출력하지 않는다.
5. 종료 코드와 산출물을 확인해 보고한다. 서버는 포트·응답과 중지 방법을 기록한다. 실패 시 원인을 확인한 뒤 재시도하며 같은 실패를 무한 반복하지 않는다.
6. 정리는 이 실행에서 기록한 PID·칸·임시 파일에만 한다. 이름으로 프로세스를 일괄 종료하거나 공용 `/tmp` 파일을 지우지 않는다. 검증 근거는 필요한 만큼 보존한다.

배포는 작업의 승인 범위와 해당 제품 절차를 따른다. 이 안내가 새 외부 작업의 권한을 주지는 않는다. 카사텀 앱 검증·배포라면 `guide develop`을 읽는다.
